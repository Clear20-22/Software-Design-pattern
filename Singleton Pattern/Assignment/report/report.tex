\textbf{Note:} Lazy is not thread-safe. In concurrent access, it produced multiple instances and multiple clients.

\subsection{Why Lazy Is Not Thread-Safe}

The lazy singleton uses a check-then-create pattern. If two threads enter \texttt{\_\_new\_\_} at the same time, both can see \texttt{\_instance is None} before either one assigns the object. That creates a race condition.

\begin{verbatim}
class LazySingleton:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            # Race window: two threads can both pass this check
            cls._instance = super().__new__(cls)
        return cls._instance
\end{verbatim}

Without a lock around the creation block, the implementation is not thread-safe by design.

\textbf{Conclusion:} Lazy failed the concurrent load test, while the other implementations maintained a single instance.

\subsection{Observations}

\subsection{Recommendations}

\begin{itemize}
    \item \textbf{Best Overall:} Enum or Bill Pugh (fast, thread-safe by design)
    \item \textbf{Balanced:} Eager Singleton (simple, good performance)
    \item \textbf{Avoid:} Lazy (not thread-safe) and Synchronized (poor performance)
\end{itemize}

\section{Conclusion}

All six Singleton implementations maintain single instances in single-threaded validation. Under concurrency, Lazy is not thread-safe and failed the thread test. Performance varies significantly, with Enum and Bill Pugh offering optimal throughput (0.0282--0.0354 \textmu s per access).
